## Key Design Decisions

### 1. Dual-Level Idempotency
**Decision**: Track both requestId and transactionId  
**Rationale**: 
- requestId prevents duplicate API requests
- transactionId prevents duplicate business transactions across channels
- Comprehensive deduplication coverage

### 2. Sequence-Based Out-of-Order Handling
**Decision**: Process transactions in strict sequence order per account  
**Rationale**:
- Strict ordering guarantees for financial transactions
- Prevents balance inconsistencies
- Clear audit trail

**Trade-offs**:
- Can block processing if sequence gaps exist
- Requires buffer management
- Mitigation: Timeout mechanism, gap detection and alerting

### 3. Retry with Transient/Permanent Failure Distinction
**Decision**: Distinguish between transient and permanent failures  
**Rationale**:
- Transient failures should be retried (network, database connection)
- Permanent failures should not be retried (insufficient funds, validation errors)
- Efficient use of retry attempts

### 4. In-Memory Stores for Assessment
**Decision**: Use ConcurrentHashMap for persistence  
**Rationale**:
- Simple and fast for assessment purposes
- Thread-safe operations
- No external dependencies

**Production Path**: Replace with PostgreSQL/MySQL + Redis

### 5. Fail-Fast Validation
**Decision**: Validate before processing, isolate failures  
**Rationale**:
- Invalid transactions don't stop batch processing
- Clear error messages
- Efficient resource usage
